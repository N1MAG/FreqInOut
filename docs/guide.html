FreqInOut User Guide

Current version: 1.2.3

This guide is a complete reference for the current FreqInOut interface. It documents each main-menu area, tab, button, table, and nested action so both new and advanced operators can move quickly and confidently.

Time model: schedule and SOP data are stored in UTC. Local/UTC toggles change display only.

How to use this guide: if you are new, read the sections in operational order instead of treating this as a pure control catalog. Start with Settings and Multi-Rig Configuration, then the schedule tabs, then the live operating tabs such as ControlFreq, Messages, and Map. If you are already operating, use the guide as a workflow map: when one tab seems confusing, the answer is often explained in a related tab or settings section.

  • How: each section explains what the controls do.
  • Why: each major tab also explains what operational problem it solves so you know when to use it.
  • Where it interacts: FreqInOut is intentionally cross-connected. In multi-rig, many surfaces also depend on which device is currently the Station Default shell.
Tip: if a button appears muted, it usually means no eligible action is available yet. Select a row, start a net, or complete required fields to enable the next step.

Quick Start

Goal: build a multi-radio station in the same order the application expects to reason about it. Multi-rig becomes much easier to use when you think in layers: operator identity first, then device definitions, then operating profiles, then assignments, then schedules, then operating tabs. Quick Start is intentionally explanatory so a new user understands not only what to click, but why the sequence matters.

  1. 1) Begin with Operator Information: callsign, name, state, and grid still matter globally in multi-rig. These values drive filenames, compose defaults, operator matching, map context, and several station-level workflows even though device control is split across profiles.
  2. 2) Read Multi-Rig Configuration before building anything else: this section explains the most important concept in the current design, which is that one device acts as the Station Default compatibility shell even while other devices may be active. If you understand that idea early, the rest of Settings becomes much more intuitive.
  3. 3) Build Device Profiles first: define each radio or observer endpoint, its control method, launch behavior, shared RF/PTT groups, and device-local VarAC data. Device Profiles are the source of truth for what each radio actually is.
  4. 4) Build Operating Profiles next: decide how each device should behave when it becomes the Station Default shell. This is where you choose whether scheduler automation, Messages, Map, Launch Control, and other major surfaces are active for that operating style.
  5. 5) Apply Device Assignments and choose the Station Default: assignments connect devices to operating intent. The Station Default selection determines which radio the legacy/core tabs are currently projecting. This is why a user can have several active radios but still see one primary shell in ControlFreq, Messages, and most operating tabs.
  6. 6) Configure projected software sections only after the Station Default is understood: review JS8Call Settings Details, Fast Light Settings Details, and VarAC Settings Details as the current projection of the Station Default device. These sections are still important, but in multi-rig they are easier to understand after the device/profile/assignment model is clear.
  7. 7) Add optional station-wide helpers only after the primary device model works: use Custom Tools Details for scripts and helper launchers that are not radio-specific integrations, then review Launch Control if you want FIO to launch software for the current shell.
  8. 8) Build your operating plan: define your shared operating logic in HF Operating Groups, then create schedules in HF Daily and HF Nets. In multi-rig, schedules only make good sense after the Station Default and assignment logic are settled.
  9. 9) Use Station Overview as your truth-check: confirm which device is the current Station Default, which profiles are active, whether temporary overrides are in effect, and whether RF/PTT or VarAC cluster warnings need attention. This tab is one of the most important “why does the app look this way right now?” tools in multi-rig.
  10. 10) Validate the live operating picture in FreqPlanner and ControlFreq: FreqPlanner helps verify plan logic; ControlFreq shows what the current Station Default shell believes it should do now. If either looks wrong, revisit Settings and Station Overview before assuming the scheduler is incorrect.
  11. 11) Move into operating tabs only after the shell is trustworthy: use Messages, Map, and SOP Builder once the device and assignment model is stable. These tabs are powerful, but they are much easier to interpret when you already know which radio/profile shell they are following.
  12. 12) Use the NCS tabs only for active role-based operation: FLDigi / SSB, JS8Call, and VHF/UHF assume you already have a coherent multi-rig station definition and now need operating support for a specific net-control role.
Recommended first-run mindset: in multi-rig, do not start with the schedule tabs. Start by teaching FreqInOut what radios exist, how they behave, and which one currently owns the compatibility shell. Once that foundation is correct, schedule behavior and operating tabs become much easier to trust.

Multi-Rig Configuration

Purpose: configure multiple device profiles while keeping the current 1.2.2 compatibility shell predictable.

Compatibility model: one or more device profiles can be runtime-active at the same time, but exactly one non-observer device is the Station Default. Current tabs such as ControlFreq, FreqPlanner, Messages, Map, scheduler control, launch behavior, and the NCS tabs continue to follow that Station Default device unless this guide explicitly says otherwise.

Observer / SDR note: Observer / SDR device profiles can be active and visible in Station Overview, but they never become the Station Default shell and cannot be used as temporary-swap targets.

Recommended Setup Order

  1. 1) Build Device Profiles first: create one row for each radio/control endpoint you want to manage. This is where you define control backend, deployment mode, backend endpoints, launch path, device-local VarAC paths, optional observer/SDR endpoint, and shared resource labels such as PTT Group, Antenna Group, Front-End Group, and Amplifier Group.
  2. 2) Mark the runtime-active devices and choose one Station Default: use Activate for devices that should participate in the running station, then use Set Station Default on the one device that should drive the current compatibility shell. Existing primary tabs continue to control that device.
  3. 3) Create Operating Profiles: define the shell policy you want a device to use when it becomes the Station Default. This is where you enable or suppress scheduler automation, Messages, Map, background ingest, Launch Control, and the net-control tabs. Preferred bands and Allow profile swap coordination also live here.
  4. 4) Apply Device Assignments: assign the intended operating profile to each device. Use Temporary Override when you want a different shell policy now without rewriting the baseline assignment, and use Restore Default when that temporary policy is no longer needed.
  5. 5) Use Temporary Swap... only when you need to move the Station Default runtime temporarily: the recommended mode is Use target device profile, which changes the Station Default device without rewriting that target device's current effective profile. Carry current primary profile is only available when the current primary operating profile explicitly allows it.
  6. 6) Group shared transmit and RF resources before operating: matching PTT Group values create hard shared-PTT protection, while matching antenna/front-end/amplifier groups raise prompt-first RF conflict warnings before scheduler or QSY changes proceed.
  7. 7) Configure device-local VarAC data in Device Profiles before you build clusters: per-device VarAC install path, DB path, INI path, and optional launch command stay with the device profile. Shared-cluster identity is configured later in VarAC Clusters and VarAC Memberships.
  8. 8) Create VarAC clusters, then memberships, then select the gateway handler: create the cluster record first, assign enabled non-observer devices with unique instance numbers, and then return to the cluster editor to choose the gateway handler from the enabled members.
  9. 9) Confirm the result in Station Overview before trusting live control: verify the Station Default badge, active device cards, shared PTT/RF warnings, observer follow guidance, VarAC cluster summaries, and any temporary-swap notices.

  • Cross-tab interaction: ControlFreq reflects results from Settings, Device Profiles, Device Assignments, HF Daily, HF Nets, SOP Builder, Messages, and the software status providers.

Messages

Purpose: unified traffic review, filtering, read state, and file-level actions.

Why you use it: Messages is where FreqInOut turns many traffic sources into one operational inbox. In multi-rig, it still follows the Station Default shell, so this tab answers “What traffic belongs to the radio bundle I am currently operating?”

  • Traffic model: some rows are files, some are software-originated message artifacts, and some are reporting artifacts that also influence Map and operator-history views.
  • Cross-tab interaction: if a report changes Map pins or SitRep rollups, the original artifact is usually visible here. If a BBS or compose workflow seems confusing, pair this section with VarAC Settings Details.
  • Best habit: use filtering aggressively. As traffic volume grows, focused views are more useful than trying to interpret the full combined inbox all at once.

CommStat and SitRep note: status-bearing CommStat and JS8Spotter traffic still feeds the shared SitRep model used by Map, Operator History, and latest-status views. The Messages tab now also surfaces first-class CommStat artifact rows as CommStat StatRep, CommStat Message, and CommStat Alert. This means operators can review the original CommStat artifact without losing the normalized shared SitRep view used for pinning and rollups.

Concept note: a SitRep in FreqInOut is the normalized operational-status view, not necessarily the original message format. CommStat, JS8Spotter, local NCS inputs, and other sources may all describe status differently. FreqInOut preserves the original artifact here in Messages, but Map and rollup surfaces often use the normalized SitRep layer so operators can compare status consistently across sources.

CommStat filtering: use MSG Type for CommStat, CommStat/StatRep, CommStat/Message, and CommStat/Alert. Use the To filter to narrow by report group or target, including groups discovered from live CommStat traffic even when they are not part of your configured operating groups.

CommStat dedupe: FIO now merges near-time mirrored CommStat status artifacts so the same real report is not shown twice when it is seen through CommStat tables and JS8Spotter-adjacent paths. The fused SitRep model stays responsible for map pinning and latest status by callsign.

Compose and Staging

  • Mode switch: use Inbox and Compose to move between received traffic review and outbound form staging.
  • Compose setup: choose form family and template, priority, send target, optional VarAC copy target, and report title before staging files.
  • Report title: keep the title short and file-safe. FreqInOut removes spaces and minimizes punctuation in the staged filename.
  • Refresh Forms: reloads the available NBEMS forms from your configured source folders without restarting the app.
  • Open Source Folder: opens the source folder for the currently selected form family so you can confirm templates or supporting files.
  • VarAC copy choices: when selected, FreqInOut stages the finished file and then copies it to the configured VarAC destination such as Outbox or BBS.
  • FLAmp signing flow: when the compose destination includes FLAmp, signing options apply only to the staged FLAmp output. Signature verification for received traffic remains governed by Settings > Message Auth (Key/Hash).

BBS Archive and Auto-Archive

Use this to keep your BBS folder clean without deleting files.

  • BBS concept: in VarAC, the BBS Directory is the live folder remote stations can browse and pull from. It is not the same as Incoming Files, which is where files addressed to you arrive, and it is not the same as Outbox, which is where files you want to send directly are staged.
  • Ordinary workflow: use +BBS or a compose-stage copy choice when you want a file offered through the VarAC BBS. Use Outbox when you want VarAC to send a file directly to a station instead of publishing it for later pickup.
  • Manage VarAC BBS & Vault: opens Settings > VarAC Settings, which is the authoritative place to configure BBS folders, access controls, Managed BBS Vault, and INI sync for the current Station Default radio context.
  • Managed BBS Services concept: FreqInOut keeps the live BBS path stable for VarAC while publishing a virtual menu and selected file set into that folder. Think of it as changing what the BBS is offering without changing the BBS directory path itself.
  • Virtual folders: menu names such as DOCDROP, INTEL, MISC, and ROOT are virtual aliases, not real nested folders inside the live BBS directory.
  • When to use Managed BBS Services: use the normal BBS workflow when one shared BBS folder is enough. Use Managed BBS Services when you need controlled alternate file sets, menu-style browsing, callsign-aware visibility, or FLAMP relay block support.
  • Manual archive: click Archive on a BBS row to move just that file now.
  • Auto-archive timing: with Enable Auto-Archive on, checks run when you first open Messages after startup, then about once per day.
  • Age rule: files older than After <days> days are moved.
  • Required setup: BBS Directory and BBS Archive must both exist and be different folders.
  • Archived rows: archived BBS files stay visible in Messages with an [Archived] title prefix so you can still View or Delete them from the archive folder.
  • Operational inspiration: FreqInOut's VarAC BBS management direction is informed by KG5RKW's Vault and VGuard workflows.

Local Roster and Categories

  • Category model: TFC, QRU, LATE, and Seen Locally are operational buckets that help you track who has traffic, who has none, who arrived late, and who has been observed locally but not necessarily merged into the main roster picture.
  • Roster table columns: Callsign, Name, State, Traffic, Category, and Source. This is the primary operator-facing working surface for the current net.
  • Copy actions: the copy buttons produce roster slices or a summary you can paste elsewhere without manually rebuilding the list.
  • Source awareness: the roster keeps track of where an entry came from so you can distinguish direct operator lookup insertion, reference imports, review merges, or other local workflow paths.

Compare, Reference, and Review Workspace

The expandable Compare / Reference area is a tabbed workspace for reconciling your local roster with outside lists and lower-confidence intake.

  • Reference tab: a place to paste or maintain an outside NCS list. From here you can compare that reference against your local roster and add missing entries when appropriate.
  • Compare Results tab: shows what is missing between the compared lists, lets you copy those differences, and supports merging missing entries into the local roster when that is operationally appropriate.
  • Review tab: holds lower-confidence log-assisted candidates so they can be inspected before they become real roster entries. This is a protection feature, not just a convenience surface.
  • Show/Hide: the compare workspace is collapsible so you can keep the net roster dominant when you are not actively reconciling lists.

SOP Schedule Status (HF)

This section summarizes active/inactive HF SOP status and conflict indicators, including quick SOP activation/deactivation buttons by group.

  • Active: no blocking HF, Net, or SOP conflicts are currently detected.
  • Attention: HF conflicts are clear, but Net or SOP review items still exist.
  • Conflict: blocking HF overlap still exists and should be resolved before trusting the active plan.

Step-by-Step: HF SOP Review in HF Daily

  1. 1) Open HF Daily after saving or activating an HF SOP: use this tab to verify how the baseline HF plan and the active HF SOP interact.
  2. 2) Read the SOP Schedule Status section first: if it shows Conflict, there is still a blocking HF overlap to fix. If it shows Attention, HF is clear but Net or SOP review is still needed.
  3. 3) Click Resolve Conflicts when available: the dialog summarizes only the blocking HF/SOP overlap pairs that still need action.
  4. 4) Use Auto-Adjust HF Around SOP (Reversible) when you want FreqInOut to split or trim the HF rows for you: this now saves the adjusted HF rows immediately so the status can refresh right away.
  5. 5) Turn on Show Effective Schedule to confirm the actual runtime timeline: this view is read-only and shows the exact HF/SOP sequence the scheduler will follow, including the return to the baseline HF row after an SOP window ends.
  6. 6) If you later deactivate the HF SOP, use Return to Normal when prompted: this restores the pre-SOP HF baseline from the saved reversible snapshot and writes that restored baseline back to the daily schedule.
  7. 7) Re-check the status color after restore: once the SOP is deactivated and the baseline is restored, the HF-specific conflict state should return to the normal non-conflict state unless a separate schedule issue still exists.
Tip: Show Effective Schedule is only available while an HF SOP is active. It is a verification view, not an editable schedule.

Step-by-Step: Recommended HF SOP Workflow

  1. 1) Confirm the baseline first: make sure your normal HF Daily and HF Nets schedules are already in the state you want before you start building the SOP.
  2. 2) Select HF SOP in the SOP selector: this keeps you in the HF-only workflow. Use Local Comms SOP only for local profiles and reminders.
  3. 3) Fill in the profile header: confirm the name and decide whether you want the profile to be saved as active right away.
  4. 4) Add all needed action rows before opening the workbench: complete Group, Resource, Action, Band/Freq, Start, End, and any contact details. The workbench is designed to stay collapsed while you make several row edits.
  5. 5) Use the in-line conflict badges while editing: OK means the row is currently clear, Conflict means the row still needs review, and Local identifies local-only rows that do not participate in the HF conflict flow.
  6. 6) Expand the Conflict Workbench only after the rows are mostly complete: this keeps the builder stable while you make multiple edits and reduces context switching.
  7. 7) For timing conflicts, use Suggest first: if a timing shift is possible, the suggested start will be precomputed for you. If the conflict is not time-based, the field stays neutral so it does not imply a missing required value.
  8. 8) Apply per-conflict priority only when needed: use the workbench buttons to choose SOP, Net, or Daily priority for the selected conflict row, or use the builder defaults when that matches your plan.
  9. 9) Save the SOP: Save re-runs the validations, applies required policy decisions, and updates the active-state logic.
  10. 10) Switch to HF Daily immediately after saving an active HF SOP: this is where you confirm the actual runtime sequence, run Resolve Conflicts if HF overlap still exists, and verify the final effective timeline.
  11. Rule: same-frequency SOP overlaps are allowed and are not shown as conflicts because they do not require a frequency change.

Conflict Resolution Prompts

  3. Daily Schedule Priority on Conflicts

  4. 4) When the SOP event ends, deactivate the HF SOP and accept Return to Normal: this restores the saved pre-SOP HF baseline in one step.

Device Profiles and Station Default Details

  • Runtime-active vs Station Default: Active means the device participates in runtime monitoring. Default marks the one non-observer device that owns the current compatibility shell.
  • Endpoint ownership: backend and endpoint fields in the device dialog are the per-device source of truth. Changing the Station Default re-projects that device into the legacy JS8/Fast Light/VarAC sections.
  • Observer / SDR behavior: observer profiles may be active and visible in Station Overview, but they do not become Station Default and cannot be used for temporary swaps.
  • Shared PTT: matching PTT Group values create the shared-transmit interlock. If another linked device is keyed, scheduler/QSY actions warn or block from the Station Default shell.
  • RF resource warnings: matching antenna/front-end/amplifier groups do not rewrite assignments automatically; they raise operator-readable RF conflict warnings so you can decide whether to proceed.
  • Delete rule: active device profiles cannot be deleted. Deactivate them first, and if the profile is the Station Default choose another default before removal.

Operating Profiles and Device Assignments Details

  • Operating profile purpose: an operating profile defines the compatibility shell used by the Station Default device, including scheduler automation, Messages, Map, background ingest, Launch Control, and net-control visibility.
  • Shell summary: Full shell means no feature suppression. A summary such as Messages Off or NetCtrl Off means those surfaces are suppressed when that profile is active on the Station Default device.
  • Preferred bands: this is advisory policy metadata for the assigned operating profile. It does not independently retarget current tabs by itself.
  • Assign / Override...: use Active for the normal effective profile or Temporary Override when you need a different shell policy now without rewriting the device's baseline role.
  • Restore Default: removes the effective override and returns the device to the default operating profile assignment.
  • Temporary Swap...: moves the Station Default runtime temporarily to one active non-primary non-observer device. Restore Swap returns the prior primary device and, if needed, restores the target device's prior effective operating profile.
  • Carry-profile rule: the swap dialog only offers Carry current primary profile when the current primary operating profile has Allow profile swap coordination enabled.

VarAC Clusters and Memberships Details

  • Cluster workflow: create the cluster first, then assign memberships, then return to the cluster editor to choose the gateway handler from the enabled members.
  • Cluster fields: Name, Cluster ID, optional Shared DB, refresh interval, optional PTT Lock, and gateway-handler selection.
  • Membership fields: cluster, device, instance number, enabled state, and gateway-role visibility.
  • Eligibility rule: observer / SDR device profiles are not eligible for VarAC cluster memberships.
  • Membership safety: each device may hold one enabled cluster membership in this phase, enabled instance numbers must be unique inside a cluster, and the gateway handler must be one of that cluster's enabled members.
  • Node-local settings: device-local VarAC install path, DB path, INI path, and optional launch command remain on the device profile. Clusters describe the shared relationship, not the per-device local installation.

HF Operating Groups Details

  • Condition-level concept: condition levels let you pre-stage several operational postures without rewriting the whole schedule every time conditions change. VarAC Settings Details

Concept of use: treat the VarAC paths as three different jobs. Incoming Files is where files addressed to you arrive. VarAC Outbox Directory is where FreqInOut stages files that VarAC should transmit directly. BBS Directory is the live published file shelf remote stations can browse and pull from. In multi-rig, the section shows the current Station Default projection, so always confirm which radio bundle you are editing.

  • VarAC Install Folder: the VarAC program location for the selected radio bundle. FreqInOut uses this for launch/orchestration and to help infer other VarAC resources.
  • VarAC Launch Command: advanced override. Leave this blank unless you need a special launch method, most often on Linux/Wine.
  • Incoming Files: VarAC's receive folder for files delivered to you. This is not your BBS folder.
  • VarAC Outbox Directory: where FreqInOut stages files that VarAC should send directly. Use this for operator-to-operator delivery, not public BBS publication.
  • VarAC INI File: direct path to the selected radio's VarAC.ini. Use this when auto-detection is not enough or when you want to sync BBS policy from the authoritative INI.
  • BBS Directory: the live published VarAC BBS folder for the selected radio. Remote stations see the files in this directory when they browse your BBS.
  • BBS Archive: where archived BBS files are moved. This keeps the live BBS tidy without deleting older files.
  • Enable BBS: turns VarAC BBS service on or off in FreqInOut's BBS policy view for the current radio projection.
  • Limit Access To Callsigns: restricts BBS access to a defined allow-list. This is strongly recommended if you want a controlled BBS.
  • Allowed Callsigns: the allow-list used when access limiting is enabled. FreqInOut supports lookup-assisted management to reduce typos. In multi-rig, this list belongs to the selected radio's VarAC bundle.
  • Announce: mirrors VarAC's BBS announcement behavior so users can choose whether the BBS is advertised.
  • Sync From VarAC.ini: reads the [BBS] section and applies BBS enablement, directory, access rules, and announcement behavior to the current radio-scoped VarAC view.
  • Write to VarAC.ini: pushes the current BBS policy values back into VarAC.ini when you want FreqInOut's view to become the authoritative one.
  • Enable Auto-Archive: turns on background checks (first Messages open after startup, then about daily).
  • After <days> days: older files are moved from BBS Directory to BBS Archive.
  • Managed BBS Services: the combined virtual-folder vault and FLAMP relay workflow. It publishes one selected view into the live VarAC BBS directory at a time while keeping the live folder stable for VarAC.
  • Vault vs live BBS: think of the live BBS Directory as the on-air shelf and the Managed Vault as the backstage storage plus control logic. Operators edit source folders in the vault; FreqInOut projects only the active view into the live BBS.
  • Enable Managed BBS Vault: turns on the virtual-folder and relay service processing for the projected radio bundle. Only enable it after you have a valid live BBS Directory and at least one location.
  • Initialize Managed Vault: creates the managed vault folder structure in the VarAC BBS area and imports the current live BBS contents into the default location so you can start from your existing BBS instead of rebuilding it by hand.
  • Reset To Default: republishes the default location into the live BBS folder. Use this if you want to end a special-access session immediately.
  • Managed Root: automatic FreqInOut-managed storage for named locations, audit state, and publish manifests. In the current release it is always created next to the live BBS Directory as FIO_BBS_Vault; it is not a free-form operator override.
  • Managed Root structure: the normal layout is Managed Root/locations/<Location Name> for operator-maintained source folders, plus Managed Root/runtime/manifests, runtime/logs, and runtime/tmp for FreqInOut bookkeeping.
  • Managed Root example: if your live BBS is /Users/you/Radio/VarAC_files/BBS, the vault root will be /Users/you/Radio/VarAC_files/FIO_BBS_Vault, and a location named TEST_A will normally use FIO_BBS_Vault/locations/TEST_A.
  • Manifest concept: each publish operation records what FreqInOut projected into the live BBS. That manifest lets FreqInOut reset safely, avoid clobbering unrelated live files, and explain what the last vault action actually published.
  • Default Location: the normal published BBS set for the selected Station Default radio. FreqInOut returns to this location on the selected return rule, or when you click Reset To Default.
  • Global Code Policy: decides whether alternate locations may stay public, whether non-default locations should normally require codes, or whether all restricted locations must require codes.
  • Request Parsing: Vault watches VarAC session traffic and reacts to root requests, alias opens, root returns, and FLAMP commands. The normal human workflow is still command-prefix style: refresh the root view, type the location alias, and refresh again. Compatibility parsing still accepts forms such as BBS OPEN TEST_A and exact-code-only workflows where configured.
  • Return Mode: decides when the BBS should go back to the default location. On disconnect is the most direct. After inactivity timeout is useful when disconnect lines are unreliable. Manual operator reset only keeps the special location active until you explicitly reset it.
  • Idle Timeout: used with inactivity-based return mode. Choose a value long enough to avoid interrupting a legitimate session.
  • Failed Attempts: how many bad codes are tolerated before cooldown is applied.
  • Cooldown: how long FreqInOut will ignore more bad-code attempts from that sender after the failure threshold is reached.
  • Enable FLAMP relay service: allows remote queue browsing and block requests using commands such as LIST Q, LIST BLKS F277, and BLK 0,1 F277.
  • FLAMP relay concept: this is not ordinary file browsing. It is a command-driven assist for block-based FLAMP transfer workflows. FreqInOut temporarily publishes helper files that let a remote operator discover queues, inspect available blocks, and request only the blocks they need.
  • FLAMP relay folder: the source folder where FreqInOut looks for relay queue files to advertise and serve as temporary synthetic BBS responses for the selected radio.
  • FLAMP relay auto-fill: if your FLAMP/rx path is set, FreqInOut will usually suggest a sibling relay folder automatically. This is a convenience default; you can override it whenever your station uses a different relay path.
  • Locations: named virtual folders that can be published into the live BBS. The Default location is your normal BBS. Other locations are optional controlled alternatives.
  • Location Name: operator-friendly label for the file set, such as Default, Logistics, or Exercises.
  • Alias: the short command a remote station types, such as INTEL or DOCDROP.
  • Description: the helper text shown in the root menu entry so the remote operator knows what the alias is for. The most readable pattern is a short phrase that finishes the generated instruction, such as to open Logistics.
  • Source Folder: the real folder whose files will be published when that location is active. The safest normal pattern is a dedicated folder under Managed Root/locations in the VarAC BBS area. This is where you place files from your computer when you want that location to publish them. In the current release, nested subfolders are ignored.
  • Source Folder defaults: when you create a new location, FreqInOut suggests Managed Root/locations/<Location Name>, shows likely live-BBS name matches, and can create the missing folder on save so you do not have to hand-build the layout first.
  • Enabled: whether that location can be published.
  • List In Root Menu: controls whether the alias is advertised in the root menu. Hidden locations can still exist for controlled direct access workflows.
  • Visibility: controls whether everyone sees the alias, only allowed callsigns see it, or it stays hidden from the generated root menu.
  • Open Rule: controls whether the location is public, callsign-limited, or requires both an allowed callsign and a code.
  • Inherit Global Allowed Callsigns: applies the normal BBS allow-list to that location. This is the safest default.
  • Location Allowed Callsigns: optional stricter subset for that location. Use this when a special location should be opened only by certain stations even if the main BBS allow-list is broader.
  • Access Code / Confirm Code: write-only operational code used to open a non-default location. FreqInOut stores only a salted hash and shows only Code configured in the UI. This is workflow control, not strong secrecy.
  • Root menu helper files: when the vault is at the default location, FreqInOut injects synthetic BBS helper entries into the live BBS such as BBS MSG - Type TEST_A ... then refresh BBS. These are instructions for the remote station, not operator source files.
  • Remote workflow: a caller usually sends <BLR> to refresh the root view, reads the helper entry for the location, types the alias such as TEST_A or TEST_A BLUEBELL depending on the location policy, and then refreshes again. After that refresh, the live BBS view contains the actual files from that location. ROOT, BACK, EXIT, or LOCK returns them to the main menu.
  • Location view behavior: only one vault view is published into the live BBS at a time. When a location is open, the remote station sees that location's files plus a helper entry telling them to type ROOT to return.
  • Callsign-aware menus: root menu entries can be filtered by the requestor's callsign, so a station may only see the aliases it is allowed to use.
  • FLAMP relay workflow: remote stations can ask for queue listings, available blocks, and individual block payloads without you manually swapping files in and out of the live BBS folder.
  • Save Location: stores the location definition in FreqInOut so it can be published later.
  • Remove: deletes the selected non-default location definition from FreqInOut. The Default location cannot be removed.
  • Vault runtime status: Settings, ControlFreq, and the Messages BBS summary surface the last vault action so operators can tell whether the vault is enabled, active, reset, or degraded without opening logs.
  • Recommended first setup: start with normal BBS folders and verify BBS copy/archive behavior first. Then initialize the Managed Vault, confirm the imported default location looks right, and only after that add protected alternate locations.
  • Credit: advanced VarAC BBS management in FreqInOut is being shaped with explicit credit to KG5RKW for the operational ideas behind Vault and VGuard.
  • VGuard concept: VGuard is not the same feature as Managed Vault. Vault decides what you publish into the live BBS. VGuard watches inbound VarAC file transfers and can log, delete, or quarantine files from unauthorized senders before they quietly blend into operator workflows.

Message Auth (Key/Hash) Details

Concept of use: Message authentication answers two different questions. First, “Did this file come from the signer I expected?” Second, “Did the contents change after that file was created?” FreqInOut supports both signature-based verification and hash-based verification because different operators and software workflows use different trust methods.

  • Signature vs checksum: a signature tries to prove both integrity and signer identity, as long as you trust the signing key. A checksum or hash proves only that the bytes match the expected digest; by itself it does not identify who created the file.
  • What a sidecar is: a sidecar is a separate helper file that travels next to the main file. For example, a message file may be accompanied by a separate signature file or checksum file instead of embedding that information inside the main payload.
  • Common sidecar patterns: in FreqInOut, a signed or verified FLAMP-related file might appear as the main payload plus a companion such as .sig, .sig.k2s, .sig.b2s, .k2s.sig, or .b2s.sig. The naming is not always consistent in the field, so FreqInOut tries to verify the content relationship rather than trusting only one naming style.
  • Why this matters operationally: if a file will drive action, planning, or reporting, operators should know whether they are trusting authorship, file integrity, or both. A successfully opened file is not the same thing as a verified file.
  • Trust model: verification is only as good as the trust decisions behind it. If a key is not trusted, a technically valid signature may still be operationally untrusted. Likewise, a matching checksum is useful only if you trust the source of the checksum.
  • Recommended habit: use signatures when possible for operator-to-operator trust, and use hashes as an additional integrity check or fallback when a signature workflow is not available.
  • Signature verification: Verify FLAMP .k2s/.b2s signatures tells FreqInOut to look for supported signature patterns around FLAMP-style payloads and verify them against the available trusted keys.
  • Checksum verification: Verify FLAMP .k2s/.b2s checksum sidecars tells FreqInOut to compare a payload against a separate digest sidecar when one exists. This is about file integrity, not signer identity.
  • Trusted hash actions: Add, Import Hash File, and Remove Selected manage hashes you want FreqInOut to treat as known-good reference values.
  • GPG executable path: this tells FreqInOut which local GPG implementation to use for key and signature operations. On some systems this may be gpg; on others it may be a full path.
  • GPG actions: Browse, Test, Refresh Keys, Import Key File, Import Armored Key, and Local-Sign Selected manage the local trust environment used for signature verification.
  • What an armored key is: an armored key is a text-form public key block, usually starting with -----BEGIN PGP PUBLIC KEY BLOCK-----. It is easier to share in email or plain text than a binary key file.
  • What local-sign means: locally signing a key does not change the original sender's file. It records that your local trust store considers that public key verified enough for your own operational use.
  • Key table columns: Trusted shows whether the key is currently trusted for your station, Fingerprint is the unique long-form identifier you should compare carefully, and User IDs are the human-readable identities attached to that key.
  • Trusted hash table columns: Use enables or disables that reference hash, Algorithm identifies the digest type, Hash is the expected digest value, and Label is your human-readable reminder of what that hash represents.
  • Operational caution: do not treat a matching name or callsign in a key's user ID as sufficient proof by itself. The fingerprint is the safer identity anchor.

Custom Tools Details

Concept of use: Custom Tools let you teach FreqInOut about helper programs that are specific to your station workflow but are not one of the built-in supported radio applications. Most often these are Python scripts, shell scripts, wrappers, emulators, or small utility launchers you want available from the same operational surface as the rest of the station tools.

  • Name: the operator-facing label FreqInOut shows in Settings and Launch Control. Use a short, recognizable name that tells you what the tool is for.
  • Launch Command: the exact command FreqInOut should run. This can be a script path, an executable, or a full command line with arguments if your workflow requires it.
  • What this is for: use Custom Tools for station-specific helpers that you want to launch intentionally from FIO, such as emulators, monitoring helpers, conversion scripts, or other repeat-use operational utilities.
  • What this is not for: do not use Custom Tools to replace the built-in FLRig, FLDigi, JS8Call, VarAC, or other first-class integrations unless you deliberately need a custom wrapper. Built-in integrations carry their own readiness checks and cross-tab behavior that generic tools do not.
  • Ordering: Up and Down control the order Custom Tools appear when surfaced in Launch Control.
  • Add / Edit / Remove: these manage the saved Custom Tool definitions only. They do not automatically start the tool.
  • Cross-tab interaction: configured Custom Tools also appear in Launch Control, so the same named helper can be launched alongside your station software instead of living only as an external script on disk.
  • Multi-rig scope: Custom Tools are global helpers, not radio-bound device profiles. They remain available as station utilities even though built-in software projections follow the current Station Default shell.
  • Best practice: if a command depends on a specific working directory, interpreter, virtual environment, or shell wrapper, include that intentionally in the command so the tool behaves the same way every time FIO launches it.
  • Operational caution: FreqInOut can launch a Custom Tool, but it does not automatically understand that tool's internal readiness or state unless you build a separate integration for it. Treat Custom Tools as assisted launch helpers, not as full protocol integrations.

Troubleshooting

  • If a button appears disabled, confirm required row selection or required fields.
  • If schedule behavior is unexpected, check Schedule Status first (paused/off-schedule/manual mode reasons).
  • If the wrong radio appears to own ControlFreq, Messages, Map, or an NCS tab, check Settings > Device Profiles for the current Station Default and check Settings > Device Assignments for an active temporary swap.
  • If an HF Daily or HF Nets row never becomes active, verify its Target Scope and Target against the current Station Default device and its effective operating profile.
  • If a Settings section stays highlighted, open that section and look for a missing companion field such as DIRECTED.TXT, an endpoint port, a forms path, or Incoming Files.
  • If Map, Messages, or NCS buttons disappear, review the current Station Default operating profile and deployment mode. Those surfaces can be intentionally suppressed.
  • If FLDigi offset returns unexpectedly, check Settings > FreqInOut Settings for FLDigi enforcement mode (On Schedule Change vs Prompt) and confirm whether a new schedule row transition occurred.
  • If message actions are missing (for example +BBS), verify required Settings paths are configured.
  • If VarAC does not launch from Launch Control on Linux, first clear VarAC Launch Command and test auto-launch from VarAC Install Folder. If needed, then set a custom Wine command using absolute paths.
  • If VarAC cluster warnings persist, confirm the cluster shared DB path, ensure enabled memberships have device-local VarAC settings, and make sure any multi-member cluster has one enabled gateway handler selected.
  • If JS8Spotter/CommStat launch too early, keep JS8Call earlier in Launch Control order; FreqInOut now waits for JS8 API readiness before proceeding.
  • If BBS auto-archive does not run, turn on Enable Auto-Archive, confirm both BBS paths are valid and different, then open Messages once after startup.
  • If signature/hash states are neutral, verify Message Auth settings and trusted key/hash entries.
