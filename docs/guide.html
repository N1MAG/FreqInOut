FreqInOut User Guide

Current version: 1.2.6.1

This guide is a complete reference for the current FreqInOut interface. It documents each main-menu area, tab, button, table, and nested action so both new and advanced operators can move quickly and confidently.

Time model: schedule and SOP data are stored in UTC. Local/UTC toggles change display only.

How to use this guide: if you are new, read the sections in operational order instead of treating this as a pure control catalog. Start with Settings, then the schedule tabs, then the live operating tabs such as ControlFreq, Messages, and Map. If you are already operating, use the guide as a workflow map: when one tab seems confusing, the answer is often explained in a related tab or settings section.

  • How: each section explains what the controls do and what operator decision they support.
  • Why: each major tab, tab section, and nested workflow explains what operational problem it solves so you know when to use it.
  • Where it interacts: FreqInOut is intentionally cross-connected. Schedules affect ControlFreq and Map, operator rosters affect labeling and filtering, and Settings shapes nearly every workflow in the application.
Tip: if a button appears muted, it usually means no eligible action is available yet. Select a row, start a net, or complete required fields to enable the next step.

Quick Start

Goal: get one station configured in the same order FreqInOut expects to use it, so the scheduler, message workflows, map, and launch controls all agree with each other. Quick Start is intentionally more guided than brief. If a step feels unfamiliar, follow the link in that step before moving on.

  1. Start in Settings and complete Operator Information: enter your callsign, name, state, and grid. This identity is reused throughout FreqInOut in filenames, message composition, operator matching, map context, and some automated defaults. If this section is wrong, later tabs can look confusing even when the software itself is working.
  2. Tell FreqInOut which software you actually use: in Settings, choose the software stack that belongs to your station. This matters because setup review, status LEDs, launch behavior, and readiness guidance should reflect your real workflow, not every program FreqInOut is capable of supporting.
  3. Configure the core station behavior in FreqInOut Settings Details: this is where you decide how strongly the scheduler should enforce frequency changes, how prompts should behave, and what operating assumptions FreqInOut should make while you are active. Read this section if you are unsure why ControlFreq seems advisory in one case and corrective in another.
  4. Configure the radio software sections that match your station: use JS8Call Settings Details, Fast Light Settings Details, and VarAC Settings Details as needed. Do not rush this step. These sections do more than store paths; they determine how Messages, Map, scheduler busy-state protection, launch behavior, BBS handling, and other workflows interact with the outside radio software.
  5. Add optional helpers only after the core paths work: if you use station-specific scripts or support utilities, add them in Custom Tools Details. If you plan to launch supported software from FIO, finish by reviewing Launch Control. This keeps the launch surface clean and prevents helper tools from being mistaken for primary integrations.
  6. Build your operating plan: define your baseline station logic in HF Operating Groups, then build the actual schedule in HF Daily and HF Nets. Think of Settings as the station definition and the schedule tabs as the operating plan that station will follow.
  7. Save, then read the setup review before moving on: after clicking Save Settings, use the readiness guidance shown in Settings and ControlFreq. That review is meant to catch the most common causes of “the app looks wrong” before you begin operating.
  8. Validate the plan in FreqPlanner and ControlFreq: FreqPlanner helps you inspect the schedule you built; ControlFreq shows what the live station thinks it should be doing now. If those two views disagree, the issue is usually in schedule design, group configuration, or software readiness rather than in ControlFreq itself.
  9. Move into operating tabs only after the station definition is stable: use Messages for traffic review, compose, authentication, and BBS workflows; use Map for geographic context and SitRep visibility; and use SOP Builder for condition-driven action planning. These tabs become much easier to trust once the Settings and schedule foundation is correct.
  10. If you are performing live net work, use the dedicated NCS tabs for that role: FLDigi / SSB, JS8Call, and VHF/UHF are not general setup tabs. They assume you already have a working station definition and now need role-specific operating support.
Recommended first-run mindset: finish the Settings sequence first, then the schedule sequence, then the operating tabs. If you jump straight into Messages, Map, or an NCS tab before identity, software, and schedule are coherent, FreqInOut may still be functioning correctly but the experience will feel harder to interpret.

ControlFreq

Why you use it: ControlFreq is the best first tab to watch during live operation. It answers the practical questions “What should I be doing now?”, “What is changing next?”, “Am I on schedule?”, and “Is some software activity making an immediate QSY unsafe?”

  • What belongs here: short-horizon operating decisions, temporary holds, schedule confidence, and quick status review.

  • Cross-tab interaction: ControlFreq reflects results from Settings, HF Daily, HF Nets, SOP Builder, Messages, and the software status providers. If this tab looks wrong, the cause is often upstream in one of those areas.

Messages

Purpose: unified traffic review, filtering, read state, and file-level actions.

Why you use it: Messages is where FreqInOut turns many traffic sources into one operational inbox. It is the right place to answer “What came in?”, “What still needs attention?”, “What should be staged for sending?”, and “What did this report look like in its original form?”

  • Traffic model: some rows are files, some are software-originated message artifacts, and some are reporting artifacts that also influence Map and operator-history views.
  • Cross-tab interaction: if a report changes Map pins or SitRep rollups, the original artifact is usually visible here. If a BBS or compose workflow seems confusing, pair this section with VarAC Settings Details.
  • Best habit: use filtering aggressively. As traffic volume grows, focused views are more useful than trying to interpret the full combined inbox all at once.

CommStat and SitRep note: status-bearing CommStat and JS8Spotter traffic still feeds the shared SitRep model used by Map, Operator History, and latest-status views. The Messages tab now also surfaces first-class CommStat artifact rows as CommStat StatRep, CommStat Message, and CommStat Alert. This means operators can review the original CommStat artifact without losing the normalized shared SitRep view used for pinning and rollups.

Concept note: a SitRep in FreqInOut is the normalized operational-status view, not necessarily the original message format. CommStat, JS8Spotter, local NCS inputs, and other sources may all describe status differently. FreqInOut preserves the original artifact here in Messages, but Map and rollup surfaces often use the normalized SitRep layer so operators can compare status consistently across sources.

CommStat filtering: use MSG Type for CommStat, CommStat/StatRep, CommStat/Message, and CommStat/Alert. Use the To filter to narrow by report group or target, including groups discovered from live CommStat traffic even when they are not part of your configured operating groups.

CommStat dedupe: FIO now merges near-time mirrored CommStat status artifacts so the same real report is not shown twice when it is seen through CommStat tables and JS8Spotter-adjacent paths. The fused SitRep model stays responsible for map pinning and latest status by callsign.

Explain +Relay to me: viewing a file and adding it to FLAMP Relay are different decisions. View asks, “can FIO show this traffic?” +Relay asks, “can FIO safely place this file where the FLAMP relay service can advertise it by queue ID?” A complete FLAMP file received through VarAC may not have the queue ID in the filename. When the internal FLAMP file ID is exactly four hex characters, FIO uses that as the queue prefix. If the ID is missing, too long, not hex, or already belongs to a different relay file, FIO does not guess. For the relay folder and remote commands, see VarAC Settings Details.

Compose and Staging

  • Mode switch: use Inbox and Compose to move between received traffic review and outbound form staging.
  • Compose setup: choose form family and template, priority, send target, optional VarAC copy target, and report title before staging files.
  • Report title: keep the title short and file-safe. FreqInOut removes spaces and minimizes punctuation in the staged filename.
  • Refresh Forms: reloads the available NBEMS forms from your configured source folders without restarting the app.
  • Open Source Folder: opens the source folder for the currently selected form family so you can confirm templates or supporting files.
  • VarAC copy choices: when selected, FreqInOut stages the finished file and then copies it to the configured VarAC destination such as Outbox or BBS.
  • FLAmp signing flow: when the compose destination includes FLAmp, signing options apply only to the staged FLAmp output. Signature verification for received traffic remains governed by Settings > Message Auth (Key/Hash).

BBS Archive and Auto-Archive

Use this to keep your BBS folder clean without deleting files.

  • BBS concept: in VarAC, the BBS Directory is the live folder remote stations can browse and pull from. It is not the same as Incoming Files, which is where files addressed to you arrive, and it is not the same as Outbox, which is where files you want to send directly are staged.
  • Ordinary workflow: use +BBS or a compose-stage copy choice when you want a file offered through the VarAC BBS. Use Outbox when you want VarAC to send a file directly to a station instead of publishing it for later pickup.
  • Manage VarAC BBS & Vault: opens Settings > VarAC Settings, which is the authoritative place to configure BBS folders, access controls, Managed BBS Vault, and INI sync.
  • Managed BBS Services concept: FreqInOut keeps the live BBS path stable for VarAC while publishing a virtual menu and selected file set into that folder. Think of it as changing what the BBS is offering without changing the BBS directory path itself.
  • Virtual folders: menu names such as DOCDROP, INTEL, MISC, and ROOT are virtual aliases, not real nested folders inside the live BBS directory.
  • When to use Managed BBS Services: use the normal BBS workflow when one shared BBS folder is enough. Use Managed BBS Services when you need controlled alternate file sets, menu-style browsing, callsign-aware visibility, or FLAMP relay block support.
  • Manual archive: click Archive on a BBS row to move just that file now.

Purpose: Station Health shows what FIO knows about the programs and scheduler checks that can affect station control.

  • Operator Lookup/Add: type a callsign, name, and state, or start typing a known operator. FIO can complete known operators from the operator database. Then choose Add to TFC, Add to QRU, or Add to LATE. The add buttons place the station directly into the roster category you intend.
  • TFC: use this for stations with traffic. Traffic can be marked as 1PP for one priority piece or 1RR for one routine piece. FIO uses the PP/RR value when building the default roster order.
  • QRU: use this for stations that checked in with no traffic. QRU rows are still part of the net roster and can still be copied or saved.
  • LATE: use this for late check-ins or end-of-net additions. It keeps those entries visible as a separate category while still preserving them in the final roster.
  • Roster columns: #, Directed By, Acked By, Callsign, Name, State, Keyword, Traffic, TFC Status, Category, and Notes. Think of this as the working net sheet, not a static export.
  • The number column: the # column is the check-in sequence. It records the order in which stations were added to the roster. Some NCS reports are built in check-in order, so FIO keeps that order available even when the screen is sorted another way.
  • Keyword and traffic parsing: some nets put a keyword between state and traffic, such as W1ABC / Joe / FL / Psalms 4:20 / 1PP.   • Duplicates: if the same callsign is entered more than once, FIO merges it into one corrected row instead of cluttering the table with duplicates.
  • Notes: notes are for local operator awareness, such as a welfare concern, relay note, or follow-up reminder. Notes are not included in copied radio text or live macro files, so private context is not transmitted by accident. End Net saves noted rows to a separate notes archive.

This is the unusual part of the tab, and it is also the most powerful. The live action buttons do two related things: they copy text to your clipboard, and they keep macro-readable files current for operators who transmit with FLDigi macros. You can use either method. You do not have to use both.

  • Action For: choose the roster scope before clicking a live action. NCS means stations directed by NCS, including shared rows. ANCS means stations directed by ANCS, including shared rows. Shared means only rows directed by both roles. All means the full roster, ignoring Directed By.
  • ACK Needed: this copies the stations that still need an acknowledgement for the selected role. If Action For is NCS, FIO finds stations directed by NCS that NCS has not ACKed yet, copies those station lines, and then marks them ACKed by NCS. ANCS works the same way for ANCS.   • Next TFC: this is for the traffic-handling part of the net. With NCS or ANCS selected, each click picks the next directed TFC station for that role and copies the callsign twice, for example W1ABC W1ABC. The repeated callsign matches common radio practice for clarity. The row changes from Pending to Now, and previously selected rows become Called. When no more traffic stations are available, FIO clears the current next-traffic file so a macro does not replay an old callsign.
  • TFC / QRU / LATE: these copy the selected category using the current Action For scope. For example, with ANCS selected, QRU copies QRU stations directed by ANCS. With All selected, it copies the whole QRU category.
  • All Check-ins: this copies every station in the selected scope. Use Action For: All when you want the full roster, or NCS/ANCS when you only want the stations managed by that role.
  • Stations to Relay: this compare action is for the ANCS/NCS mismatch case. If your local roster has stations the partner list does not, FIO shows the stations that should be relayed back to the partner.
  • Copy Relays: select one or more relay rows, then copy them for paste into TX. FIO also writes the current relay selection to the role-specific relay file so macro-based operators have the same text available.
  • Action status: after a live action, FIO shows a short message near the buttons and then clears it. Routine live-net actions do not interrupt you with an OK popup.
  • Save Check-ins: generated macro files update automatically as the roster changes. Save Check-ins is a manual checkpoint and final-log helper; it is not required before using ACK Needed, Next TFC, or the category files. FIO highlights it when roster edits have not yet been saved.

Scheduler Behavior Examples

Explain this to me: the scheduler is FIO's way of keeping each radio matched to its current operating plan. The plan may say which frequency to use, which mode belongs with that row, and which digital offset should be used. FIO's job is to notice when the station drifts away from that plan and either fix it or ask you, depending on your settings.

The big idea: FIO is the plan owner when the scheduler is enabled. That does not mean FIO should blindly fight the operator. It means FIO keeps asking, “does this radio match the plan right now?” If not, FIO follows the choices you made in Settings. It also respects active transmit protection and multi-rig shared-resource protection, because changing a keyed or shared radio at the wrong time is not safe.

Where the plan comes from: routine HF schedule rows are the baseline. Net schedule rows can take priority during a named net. Active SOP layers can take priority when an SOP is active. ControlFreq shows the current plan and the next likely change; HF Daily, HF Nets, SOP Builder, and Radio Profiles are where you correct the plan itself.

For example, common check-in forms are marked for Net Control, SitRep forms are marked for status/map use, and alert-type forms are marked for alert handling. Treat this as a starting point. Your group may use a form differently, and you can change the purpose or checkboxes before saving.

This is the plain-language label FreqInOut uses to decide whether a form is a net check-in, a situation report, a weather report, a net notice, an information request, or something else.   • Status: lets a JS8Spotter form feed the shared status view when FreqInOut knows how to read that form's status fields. Today this is intentionally conservative: F!104, F!301, and F!304 can become normalized status. Other JS8Spotter forms can still be routed to Messages, Map, Alerts, or Net Control, but deeper status field reading requires explicit support.

HF Operating Groups Details

  • Purpose: HF Operating Groups are the reusable building blocks behind schedule rows. They describe the normal frequency, mode, VFO, FLDigi mode, and offset a group expects to use.
  • Mode choices: choose Digi for digital-mode work such as JS8 or FLDigi workflows, and SSB for voice net work.
  • Voice sideband behavior: when Mode=SSB, FLDigi Starting Mode defaults to band-appropriate sideband (LSB on lower HF bands, USB on upper HF bands), and can be manually overridden.
  • Key table columns: Group, Mode, Band, Freq (MHz), VFO, FLDigi Starting Mode, FLDigi Offset, Auto-Tune, Use Condition Levels.
  • Freq (MHz): enter the operating frequency in MHz, such as 7.078. This is the value FIO compares against the active schedule.
  • VFO: choose the radio VFO the plan expects, usually A unless your station has a reason to use another VFO.
  • FLDigi Offset meaning: this is the expected FLDigi audio offset for the group row, such as 900. If a schedule row omits FLDigi offset, the matching Operating Group value is used as the expected offset.
  • Auto-Tune: tells FIO this group is allowed to tune automatically when schedule enforcement calls for it. Leave it off when you want the operator to confirm changes manually.

  • Condition levels: group-scoped; changing one row applies to all rows for the same Group.
  • Condition-level concept: condition levels let you pre-stage several operational postures without rewriting the whole schedule every time conditions change. Instead of editing frequency plans during an event, you can move the station's active level and let FreqInOut reveal only the rows meant for that level.

VarAC Settings Details

Concept of use: treat the VarAC paths as three different jobs. Incoming Files is where files addressed to you arrive. VarAC Outbox Directory is where FreqInOut stages files that VarAC should transmit directly. BBS Directory is the live published file shelf remote stations can browse and pull from.

  • Recommended first setup: start with VarAC Install Folder, Incoming Files, and the normal BBS folders. Confirm basic send/receive and BBS behavior before enabling Managed BBS Services or VGuard.
  • VarAC Paths and Launch: section for the VarAC application path, launch command, INI path, incoming-file folder, and outbox folder.
  • BBS Management: section for the live BBS folder, BBS archive folder, BBS access settings, and allowed callsigns.
  • BBS Vault Settings: section for Managed BBS Services, vault session settings, FLAMP relay, and FIO managed locations.
  • BBS VGuard Settings: separate section for inbound file protection. VGuard is not the same service as the vault.
  • VarAC Install Folder: the VarAC program location. FreqInOut uses this for launch/orchestration and to help infer other VarAC resources.
  • VarAC Launch Command (Advanced): advanced override. Leave this blank unless VarAC needs a special start command on your station, most often on Linux/Wine.
  • VarAC Incoming Files: VarAC's receive folder for files delivered to you. This is not your BBS folder.
  • VarAC Outbox Directory: where FreqInOut stages files that VarAC should send directly. Use this for operator-to-operator delivery, not public BBS publication.
  • VarAC INI File: optional direct path to VarAC.ini. Use this when auto-detection is not enough or when you want to sync BBS policy from the authoritative INI.
  • BBS Directory: the live published VarAC BBS folder. Remote stations see the files in this directory when they browse your BBS.
  • BBS Archive: where archived BBS files are moved. This keeps the live BBS tidy without deleting older files.
  • Auto-Archive Policy: group containing Enable Auto-Archive, After, and days. It moves files older than the selected age from BBS Directory to BBS Archive.
  • Enable BBS: turns VarAC BBS service on or off in FreqInOut's BBS policy view.
  • Limit Access To Callsigns: restricts BBS access to a defined allow-list. This is strongly recommended if you want a controlled BBS.
  • Allowed Callsigns: the allow-list used when access limiting is enabled. FreqInOut supports lookup-assisted management to reduce typos. In single-rig, this list applies to the station's VarAC BBS policy.
  • Announce: mirrors VarAC's BBS announcement behavior so users can choose whether the BBS is advertised.
  • Import VarAC BBS Settings: reads the [BBS] section from the configured VarAC INI File and applies BBS enablement, directory, access rules, and announcement behavior to the current FreqInOut settings view.
  • Apply VarAC BBS Settings: writes the current BBS policy values back into the configured VarAC INI File when you want FreqInOut's view to become the authoritative one for the VarAC [BBS] section.
  • Managed BBS Services: the combined virtual-folder vault and FLAMP relay workflow. It publishes one selected view into the live VarAC BBS directory at a time while keeping the live folder stable for VarAC.
  • Vault vs live BBS: think of the live BBS Directory as the on-air shelf and the Managed Vault as the storage room plus menu system behind it. VarAC only needs to know about the live shelf. FreqInOut decides which vault location is placed on that shelf right now.
  • Managed BBS Services: label above the main vault controls. This is where Enable Managed BBS Vault, Initialize Managed Vault, and Reset To Default live.
  • Enable Managed BBS Vault: turns on the service that watches VarAC session traffic and publishes managed views into the live BBS folder. This is the operational on/off switch for the vault workflow; it does not erase your vault folders.
  • Turn on FIO-managed BBS menus.: the short UI explanation shown beside Enable Managed BBS Vault.
  • Initialize Managed Vault: creates the managed vault folder structure in the VarAC BBS area and imports the current live BBS contents into the default location so you can start from your existing BBS instead of rebuilding it by hand. After you confirm the import, the live BBS folder should be treated as FreqInOut's published output, not the long-term storage place for managed files.
  • Create the FIO_BBS_Vault folders next to the live VarAC BBS folder.: the short UI explanation shown beside Initialize Managed Vault.
  • Reset To Default: republishes the default location into the live BBS folder. Use this when you want the BBS to go back to the main menu immediately, for example after a caller opened a controlled location or after testing a special view.
  • Return callers to the root BBS menu and publish the helper files.: the short UI explanation shown beside Reset To Default.
  • Managed Root: automatic FreqInOut-managed storage for named locations, audit state, and publish manifests. In the current release it is always created next to the live BBS Directory as FIO_BBS_Vault; it is not a free-form operator override.
  • Managed Root structure: the normal layout is Managed Root/locations/<Location Name> for operator-maintained source folders, plus Managed Root/runtime/manifests, runtime/logs, and runtime/tmp for FreqInOut bookkeeping.
  • Managed Root example: if your live BBS is /Users/you/Radio/VarAC_files/BBS, the vault root will be /Users/you/Radio/VarAC_files/FIO_BBS_Vault, and a location named TEST_A will normally use FIO_BBS_Vault/locations/TEST_A.
  • Manifest concept: each publish operation records what FreqInOut projected into the live BBS. That manifest lets FreqInOut reset safely, avoid clobbering unrelated live files, and explain what the last vault action actually published.
  • Vault Session: section for default-menu identity, timers, bad-code behavior, request parsing, and FLAMP relay options.
  • Default Location: read-only display for the FIO-managed root BBS menu. This is not the same thing as the VarAC BBS Directory. The VarAC folder is the live shelf callers browse; Default is the managed source view that FIO publishes there when the BBS is at the main menu. The adjacent Info button explains this distinction in the UI.
  • Why Default exists: it gives the caller a predictable starting point. The default view normally contains helper files such as BBS MSG - Type INTEL to open Intel then refresh BBS.txt, not every file from every location. That keeps the first BBS listing readable and lets callers choose the location they need.
  • Global Code Policy: the station-wide default for how cautious alternate locations should be. The normal friendly default is to allow public locations, then set access rules per location. Use stricter global policy only when your operating plan says non-default locations should normally require codes.
  • Request Parsing: controls how FIO recognizes caller commands in VarAC traffic. The normal mode is command-prefix style: a caller refreshes the BBS, types an alias such as INTEL, then refreshes again. Compatibility parsing also accepts more explicit forms such as BBS OPEN INTEL. Exact-code-oriented workflows are available for stations that want the code itself to be the access command, but alias-plus-code is usually easier to explain on-air.
  • Return Mode: decides when the BBS goes back to the Default menu. On disconnect is the cleanest normal choice because each caller gets a fresh menu. After inactivity timeout is useful when disconnect lines are unreliable. Manual operator reset only is for deliberate operator-controlled sessions where a special location should remain published until you reset it.
  • Return Timer: used with inactivity-based return behavior. Choose a value long enough that a slow operator has time to read, request, and refresh without being pushed back to the main menu mid-session.
  • Bad Code Limit: how many bad codes are tolerated before cooldown is applied. This is a guardrail against repeated mistakes or guessing, not a cryptographic security system.
  • Cooldown: how long FIO waits before accepting another bad-code attempt from that sender after the failure threshold is reached. It keeps a caller from hammering the same protected location while still allowing them to try again later.
  • FLAMP Relay: row that contains Enable FLAMP relay service, the relay folder field, and a Browse button.
  • Enable FLAMP relay service: allows remote queue browsing and block requests. LIST Q lists available FLAMP files. LIST F277, LIST BLKS F277, and LIST BLOCKS F277 show the blocks FIO knows about for queue F277. BLKS 0,1 F277, BLK 0,1 F277, BLOCK 0,1 F277, and BLOCKS 0,1 F277 request a temporary BBS file containing those blocks.
  • FLAMP relay concept: this is not ordinary file browsing. It is a command-driven assist for block-based FLAMP transfer workflows. FreqInOut temporarily publishes helper files that let a remote operator discover queues, inspect available blocks, and request only the blocks they need.
  • FLAMP relay folder: placeholder text in the relay folder field. This is the source folder where FreqInOut looks for relay queue files to advertise and serve as temporary synthetic BBS responses.
  • Limit FLAMP listing to files newer than: limits queue listings to recent relay files, with choices such as 3 days, 5 days, 7 days, 10 days, 14 days, and 30 days.
  • FLAMP relay auto-fill: if your FLAMP/rx path is set, FreqInOut will usually suggest a sibling relay folder automatically. This is a convenience default; you can override it whenever your station uses a different relay path.
  • FIO Managed Locations: section for named virtual folders that can be published into the live BBS. The table columns are Name, Alias, Filesystem Location, Enabled, Visible, and Code Active.
  • New Location: starts a new managed location definition.
  • Save Location: stores the current location definition in FreqInOut so it can be published later.
  • Delete Location: deletes the selected non-default location definition from FreqInOut. The Default location cannot be deleted.
  • Locations: named virtual folders that can be published into the live BBS. The Default location is your root BBS menu. Other locations are optional controlled alternatives.
  • Location Name: operator-friendly label for the file set, such as Default, Logistics, or Exercises.
  • Alias: the short command a remote station types, such as INTEL or DOCDROP.
  • Custom Helper Text: optional operator-written text appended to the generated helper filename. FIO writes the command instruction automatically; your custom text should tell the caller what the location holds. For example, the generated portion might say Type AIB to open AIB then refresh BBS, and your custom text might add weekly AIB reports.
  • Helper Filename: live preview of the helper file name FIO will publish for this location in the root BBS menu.
  • Location Folder: the managed folder whose files will be published when that location is active. The safest normal pattern is a dedicated folder under Managed Root/locations in the VarAC BBS area. This is where you place files from your computer when you want that location to publish them. In the current release, nested subfolders are ignored.
  • Location Folder defaults: when you create a new location, FreqInOut suggests Managed Root/locations/<Location Name>, shows likely live-BBS name matches, and can create the missing folder on save so you do not have to hand-build the layout first.
  • Enabled: table checkbox/column for whether that location can be published.
  • Visible in Root Menu: controls whether the alias is advertised in the root menu. Hidden locations can still exist for controlled direct-access workflows.
  • Visible: table column that mirrors whether the location is visible in the root menu.
  • Access Policy: controls whether the location is public, callsign-limited, requires an access code, or requires both an allowed callsign and a code.
  • Inherit Global Allowed Callsigns: applies the normal BBS allow-list to that location. This is the safest default.
  • Location Allowed Callsigns: optional stricter subset for that location. Use this when a special location should be opened only by certain stations even if the main BBS allow-list is broader.
  • Access Code / Confirm Code: operational code used to open a non-default location. FIO stores the code locally for the station operator to view later and also keeps a hash for caller verification. This is workflow control for off-grid operations, not strong secrecy; if a code changes, you still need an operational way to share the new code with the right stations.
  • Root menu helper files: when the vault is at the default location, FreqInOut injects synthetic BBS helper entries into the live BBS such as BBS MSG - Type TEST_A ... then refresh BBS. These are instructions for the remote station, not operator source files.
  • Remote workflow: a caller usually sends <BLR> to refresh the root view, reads the helper entry for the location, types the alias such as INTEL or HUBS BLUEBELL depending on the location policy, and then refreshes again. After that refresh, the live BBS view contains the actual files from that location. ROOT, BACK, EXIT, or LOCK returns them to the main menu.
  • Protected-location helper: if a caller types an alias that requires a code but does not include the code, FIO can publish a helper message for that alias instead of leaving the caller stuck in the current view. The intent is friendly: tell them what went wrong and how to try again, for example Incorrect Code provided for HUBS - try again or return to ROOT.
  • Location view behavior: only one vault view is published into the live BBS at a time. When a location is open, the remote station sees that location's files plus a helper entry telling them to type ROOT to return. The files are copied into the live BBS for pull; the source location remains in the managed vault.
  • Callsign-aware menus: root menu helper files should only be shown for aliases the caller is allowed to see. If a location is callsign-limited, stations outside that policy should not get a menu entry that invites them into a location they cannot use.
  • List in root menu: the clearest normal administration model is to list locations in the root menu and let access policy decide who sees them. Hide a location only when you deliberately want direct-access behavior with no menu advertisement.
  • FLAMP relay workflow: remote stations can ask for queue listings, available blocks, and individual block payloads without you manually swapping files in and out of the live BBS folder. The root menu can show BBS MSG - type FLAMP to see FLAMP BLOCK FILL CMDS - then refresh BBS.txt. After the caller types FLAMP, FIO publishes separate helper files such as LIST Q, LIST F277, BLKS 0,8,9 F277, and ROOT. FIO is forgiving about the request word: BLK, BLKS, BLOCK, and BLOCKS all mean "make a block file" when block numbers are included. To look before requesting, use LIST F277; BLKS F277 is treated as an incomplete block request and FIO will publish a helper notice instead of guessing.
  • Adding received FLAMP files to relay: if a complete FLAMP file arrives through VarAC, open Messages. FIO shows +Relay only when it can confidently identify the four-character queue ID from the filename or the FLAMP file content. That protects the relay list from guessed names. If +Relay is not shown, the file may still be readable, but FIO is telling you it cannot safely add it to the relay queue automatically.
  • Vault runtime status: Settings, ControlFreq, and the Messages BBS summary surface the last vault action so operators can tell whether the vault is enabled, active, reset, or degraded without opening logs.
  • Recommended Managed Vault setup: start with normal BBS folders and verify BBS copy/archive behavior first. Then initialize the Managed Vault, confirm the imported default location looks right, and only after that add protected alternate locations.
  • Credit: advanced VarAC BBS management in FreqInOut is being shaped with explicit credit to KG5RKW for the operational ideas behind Vault and VGuard.
  • VGuard concept: VGuard is not the same feature as Managed Vault. Vault decides what you publish into the live BBS. VGuard watches inbound VarAC file transfers and can log, delete, or quarantine files from unauthorized senders before they quietly blend into operator workflows.
  • Enable VGuard File Protection: turns on inbound file protection for received VarAC files.
  • VGuard mode: choose Log only, Delete unauthorized files, or Quarantine unauthorized files.
  • VGuard trust sources: choose whether files are allowed from BBS Management allowed callsigns, from callsigns marked TRUSTED in Operator History, or both. This is sender trust, not GPG/message-auth signature trust.
  • Sender validation: VGuard uses VarAC traffic-log/session evidence before applying trust. Portable forms such as W1ABC/P can match the base callsign W1ABC. If VarAC log evidence conflicts or the sender cannot be resolved, VGuard treats that as a protection event and records the reason.
  • Quarantine Dir: destination used when quarantine mode is selected. The field defaults toward Managed Root/quarantine.
  • Retry: how long VGuard waits between checks when VarAC has logged a receive event but the file is not fully visible yet.

Message Auth (Key/Hash) Details

Concept of use: Message authentication answers two different questions. First, “Did this file come from the signer I expected?” Second, “Did the contents change after that file was created?” FreqInOut supports both signature-based verification and hash-based verification because different operators and software workflows use different trust methods.

  • Signature vs checksum: a signature tries to prove both integrity and signer identity, as long as you trust the signing key. A checksum or hash proves only that the bytes match the expected digest; by itself it does not identify who created the file.
  • What a sidecar is: a sidecar is a separate helper file that travels next to the main file. For example, a message file may be accompanied by a separate signature file or checksum file instead of embedding that information inside the main payload.
  • Common sidecar patterns: in FreqInOut, a signed or verified FLAmp, VarAC, or BBS message file might appear as the main payload plus a companion such as .sig, .sig.k2s, .sig.b2s, .k2s.sig, or .b2s.sig. The naming is not always consistent in the field, so FreqInOut tries to verify the content relationship rather than trusting only one naming style.
  • Why this matters operationally: if a file will drive action, planning, or reporting, operators should know whether they are trusting authorship, file integrity, or both. A successfully opened file is not the same thing as a verified file.
  • Trust model: verification is only as good as the trust decisions behind it. If a key is not trusted, a technically valid signature may still be operationally untrusted. Likewise, a matching checksum is useful only if you trust the source of the checksum.
  • Recommended habit: use signatures when possible for operator-to-operator trust, and use hashes as an additional integrity check or fallback when a signature workflow is not available.
  • Signature verification: Verify signed .k2s/.b2s message files and signature sidecars tells FreqInOut to look for supported signature patterns around FLAmp, VarAC, and BBS payloads and verify them against the available trusted keys.
  • Checksum verification: Verify .k2s/.b2s checksum sidecars tells FreqInOut to compare a payload against a separate digest sidecar when one exists. This is about file integrity, not signer identity.
  • Trusted hash actions: Add, Import Hash File, and Remove Selected manage hashes you want FreqInOut to treat as known-good reference values.
  • GPG executable path: this tells FreqInOut which local GPG program to use for key and signature checks. On some systems this may be gpg; on others it may be a full path selected with Browse.
  • GPG actions: Browse, Test, Refresh Keys, Import Key File, Import Armored Key, and Local-Sign Selected manage the local trust environment used for signature verification.
  • What an armored key is: an armored key is a text-form public key block, usually starting with -----BEGIN PGP PUBLIC KEY BLOCK-----. It is easier to share in email or plain text than a binary key file.
  • What local-sign means: locally signing a key does not change the original sender's file. It records that your local trust store considers that public key verified enough for your own operational use.
  • Key table columns: Trusted shows whether the key is currently trusted for your station, Fingerprint is the unique long-form identifier you should compare carefully, and User IDs are the human-readable identities attached to that key.
  • Trusted hash table columns: Use enables or disables that reference hash, Algorithm identifies the digest type, Hash is the expected digest value, and Label is your human-readable reminder of what that hash represents.
  • Default FLAmp signing key: chooses which local private key FIO should use when signing outbound FLAmp traffic. Leave auto-select on if you only have one private key and do not need to choose manually.
  • Signing key passphrase: lets FIO check or save the passphrase in the operating system credential store. It is not saved directly in the normal FIO settings file.
  • Operational caution: do not treat a matching name or callsign in a key's user ID as sufficient proof by itself. The fingerprint is the safer identity anchor.

SOP Export Details

Concept of use: SOP Export text lets you add station-specific context to the PDF version of your SOP without editing the generated tables themselves. Use it for a short introduction, local handling notes, distribution reminders, or closing instructions that should travel with the exported SOP.

  • Preamble: appears before the SOP export tables. This is a good place to explain the purpose, scope, effective time, or operator context for the document.
  • Postamble: appears after the SOP export tables. This is useful for closing reminders, document-control notes, or local operating cautions.
  • Placeholders: simple placeholders such as {{operator_callsign}}, {{as_of_local}}, {{as_of_utc}}, {{scope}}, and {{timezone}} are replaced during export.
  • Best practice: keep this text short and operational. The SOP tables carry the structured information; the preamble and postamble should explain how the operator should use or share the export.

Custom Tools Details

Concept of use: Custom Tools let you teach FreqInOut about helper programs that are specific to your station workflow but are not one of the built-in supported radio applications. Most often these are Python scripts, shell scripts, wrappers, emulators, or small utility launchers you want available from the same operational surface as the rest of the station tools.

  • Name: the operator-facing label FreqInOut shows in Settings and Launch Control. Use a short, recognizable name that tells you what the tool is for.
  • Launch Command: the exact command FreqInOut should run. This can be a script path, an executable, or a full command line with arguments if your workflow requires it. If you can start it from Terminal with that command, FIO should be able to use the same command.
  • What this is for: use Custom Tools for station-specific helpers that you want to launch intentionally from FIO, such as emulators, monitoring helpers, conversion scripts, or other repeat-use operational utilities.
  • What this is not for: do not use Custom Tools to replace the built-in FLRig, FLDigi, JS8Call, VarAC, or other first-class integrations unless you deliberately need a custom wrapper. Built-in integrations carry their own readiness checks and cross-tab behavior that generic tools do not.
  • Ordering: Up and Down control the order Custom Tools appear when surfaced in Launch Control.
  • Add / Edit / Remove: these manage the saved Custom Tool definitions only. They do not automatically start the tool.
  • Cross-tab interaction: configured Custom Tools also appear in Launch Control, so the same named helper can be launched alongside your station software instead of living only as an external script on disk.
  • Best practice: if a command depends on a specific working directory, interpreter, virtual environment, or shell wrapper, include that intentionally in the command so the tool behaves the same way every time FIO launches it.
  • Operational caution: FreqInOut can launch a Custom Tool, but it does not automatically understand that tool's internal readiness or state unless you build a separate integration for it. Treat Custom Tools as assisted launch helpers, not as full protocol integrations.

Launch Control Details

  • Launch All with FreqInOut: starts selected station tools when FIO starts. Use this when FIO is the normal front door for your operating session.
  • Enabled: decides which supported tools FreqInOut may launch from this table.
  • Launch on Startup: controls which enabled tools should auto-start with the application.
  • Order management: use Up, Down, and Reset Default Order to control startup sequencing. This matters when one tool depends on another, such as JS8Spotter or CommStat needing JS8Call to be ready first.
  • Launch Configured Now: starts the enabled tools in the displayed order without restarting FIO.
  • Stop Launch Sequence: stops an in-progress launch sequence. It does not necessarily close programs that already started successfully.
  • Custom Tool crossover: Custom Tools configured in Settings > Custom Tools also appear here, which lets you keep station-specific helpers near the same launch workflow as your built-in software stack.

Logging and Diagnostics Details

  • Logging Level: controls how much detail FIO writes to the log. Keep this disabled or low during normal use. INFO and DEBUG are best used only while troubleshooting because they can write more data and slightly reduce performance.
  • Enable DEBUG For: temporarily raises logging detail for troubleshooting and then automatically returns to the previous logging level. This is safer than leaving DEBUG on indefinitely.
  • Open Logs: opens the current log view so you can inspect recent activity.
  • Open Log Folder: opens the folder where FIO stores log files.
  • Export Diagnostics: packages logs and troubleshooting context for support review. Use this when a support helper needs more than a screenshot.

Help

Purpose: in-app documentation viewer for this guide.

  • Table of Contents (left): click headings to navigate.
  • Guide viewer (right): renders docs/guide.html.
  • Export to PDF: exports the displayed guide.
  • How to use it well: if a help button opens a specific section, read at least the purpose text and the nearby workflow notes, not only the control list. Those notes usually explain why the screen exists and what other tabs it depends on.
  • When something feels wrong: use Help as a relationship map. If a tab seems confusing, look for references to Settings, Messages, Map, Operators, or the schedule tabs nearby in the guide. Many support questions are really cross-tab workflow questions.

Off-schedule prompt note: When enforcement is set to Prompt, FIO acts like a careful helper instead of grabbing the controls. It may ask about Frequency, FLDigi Mode, or FLDigi Offset when one of those does not match the active schedule. Choose Apply when you want FIO to fix it, Ignore/Skip when you know you are off schedule and want to stay there for now, or Suspend/Pause when you want FIO to stop nudging you temporarily. The prompt interval controls how soon FIO may remind you again if the mismatch is still there.

Time and Storage Rules

  • UTC is the storage truth for schedules and SOP timing.
  • Display toggles do not rewrite stored schedule times.
  • CSV/JSON import tools validate required fields and may skip invalid rows with summary feedback.

Troubleshooting

  • If a button appears disabled, confirm required row selection or required fields.
  • If schedule behavior is unexpected, check Schedule Status first (paused/off-schedule/manual mode reasons).
  • If a Settings section stays highlighted, open that section and look for a missing companion field such as DIRECTED.TXT, an endpoint port, a forms path, or Incoming Files.
  • If FLDigi offset returns unexpectedly, check Settings > FreqInOut Settings for FLDigi enforcement mode (On Schedule Change vs Prompt) and confirm whether a new schedule row transition occurred.
  • If message actions are missing (for example +BBS), verify required Settings paths are configured.
  • If VarAC does not launch from Launch Control on Linux, first clear VarAC Launch Command and test auto-launch from VarAC Install Folder. If needed, then set a custom Wine command using absolute paths.
  • If JS8Spotter/CommStat launch too early, keep JS8Call earlier in Launch Control order; FreqInOut now waits for JS8 API readiness before proceeding.
  • If BBS auto-archive does not run, turn on Enable Auto-Archive, confirm both BBS paths are valid and different, then open Messages once after startup.
  • If signature/hash states are neutral, verify Message Auth settings and trusted key/hash entries.
